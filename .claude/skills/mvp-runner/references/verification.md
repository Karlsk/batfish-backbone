# 累计验证门槛

每篇进入 verifying 时读取本文件。实际验收范围是 MVP-01～当前篇，不是仅本次改动文件；已完成的前端、迁移、SDK、浏览器和部署验收不能因为本篇只改后端而消失。

## 1. 维护验收矩阵

在 `web/docs/validation-matrix.md` 为每篇的必要验收建立行：

`spec | 验收行为 | 自动命令及 cwd / 页面步骤 | 必需环境 | 拓扑 | 本轮结果 | 证据`

- 从原 spec、共享契约及完成记录取验收项；一条测试可覆盖多篇，但不能以重复计数冒充覆盖。每轮记录实际 collected/passed/failed/error/skipped，检查意外 deselected、xfail/xpass 和测试集合缩水。
- 尚未达到当前篇的能力标为 future，不列作本轮通过。已要求的能力缺脚本就补齐对应验证，不把“命令不存在”记为 N/A。
- 必需检查跳过、缺环境、命令失败、结果失效都阻止提交。视觉检查记录页面、操作和发现；不能仅用截图文件存在代替检查。
- 经正式契约演进替换旧测试时记录映射与原因，继续覆盖原业务约束。例如 ready 由 503 变为 200 后，真实环境断言更新，仍保留依赖缺失时不能假绿的单元测试。

## 2. 真实服务、配置输入和源码身份

实际启动步骤以 `web/docs/test-lab.md` 和当前 `web/scripts/lab.py --help` 为准。现有入口均在仓库根目录运行：

```bash
web/backend/.venv/bin/python web/scripts/lab.py serve
# serve 保持运行，后续命令在另一终端中串行执行
web/backend/.venv/bin/python web/scripts/lab.py seed
web/backend/.venv/bin/python web/scripts/lab.py smoke
web/backend/.venv/bin/python web/scripts/lab.py verify
```

- 先核对已运行服务的归属、端口、启动代码和清单；可复用正确的本机隔离环境，不因端口响应正常就接管它。只停止自己启动或明确授权管理的进程/容器。
- `lab.py serve` 当前不热重载，且数据库是临时 tmpfs。API/worker 代码、依赖、配置或迁移改变后，验收前必须重启/重建对应受控进程，确认其使用当前源码；若重启整个 lab，重新迁移、初始化测试身份并 seed。尚在执行的任务先按恢复设计处理，不通过删环境掩盖恢复缺陷。
- 两套固定配置：`web/backend/tests/fixtures/small_network`（r1/r2）与 `web/backend/tests/fixtures/cisco_four`（Cisco 四台 OSPF 菱形）。使用独立 network、不可覆盖 snapshot 和可追溯输入摘要；不要换成真实设备采集。当前清单在 `web/.runtime/test-lab/current.json`，不要硬编码旧 run ID。
- 验证实际运行的 Batfish、PostgreSQL、API、已实现 worker 和前端。可单测 mock，但不能用它替代这些必要集成环境。
- 目标是 Web 功能：上传/初始化、参数、错误、任务、结果结构、上下文及展示。已知合成配置可有确定断言；无需启动真实路由器，也不比较现场 RIB/报文转发，不将 Web 回归扩张成 Java 仿真精度研究。
- 未修改 Java 时使用已验证 JAR；变更 JAR/模板时重新核对构建来源和兼容性，不能改用官方 latest。所有使用同一引擎的验证串行，浏览器提交任务与直接 SDK 测试也不能同时争用引擎；浏览器的双用户场景仍允许并发提交，由已实现 worker 串行调度。

## 3. 每轮实际运行的检查

| 类别 | 门槛 |
| --- | --- |
| 后端 | 全部已实现后端测试、分层检查、Ruff、锁文件一致性；当前 `lab.py verify` 收集后端全套测试，不能用 `-m 'not integration'` 的结果替代累计回归 |
| 数据库/存储 | MVP-03 起实际 PostgreSQL 的空库迁移、约束、事务、文件边界；之后累计账号、任务领取、并发和恢复检查，SELECT 1 只证明连接 |
| SDK/应用集成 | 保留 SDK 基线及两套快照；业务 API 就绪后，使用两套 ZIP 经过真实上传和初始化 API，再执行已实现分析，不只从测试代码直接调用 SDK |
| 冒烟 | 本轮服务启动后执行 smoke，并随功能增加实际业务入口检查；健康 200 不能代替登录/上传/分析成功 |
| 前端 | MVP-16 起读取实际 package.json 的脚本和锁文件，执行全部已有单元测试、类型检查、构建；不用猜测的 pnpm script 名称 |
| 浏览器 | 对已实现页面按 spec 运行已有流程，覆盖本次新增/变更的实际操作和必要视觉检查；MVP-25 双用户闭环必需，不能以 Swagger、构建成功或 API 测试代替 |
| 契约/文档 | OpenAPI 与生成类型、错误、DTO、阶段状态、证据及 Markdown 链接一致；不改 spec 验收标准来迁就失败 |
| 部署 | MVP-24 起保留本机隔离全新部署、重启、备份/恢复等该篇要求；不用破坏团队环境完成验证 |

当前 `lab.py verify` **只是后端检查入口**。此前已有前端或部署能力时必须额外运行它们；可逐步扩展统一入口，但在它真正执行并产出证据前不能宣称已覆盖。

## 4. 证据有效性和提交前核对

每轮使用新的证据目录，保留必要的命令、输出/摘要、JUnit、页面证据、fixture 哈希和服务版本。运行密码、完整私有配置、数据库文件及引擎数据留在忽略提交的 `.runtime/`，不跟随 commit。

记录被测实现身份：基线 Git 提交 + 本篇所有代码/配置/依赖文件（包括未跟踪文件）的路径与内容摘要。测试后若这些文件改变，旧通过结果不能用于提交；文档/证据回写不要求重复引擎计算，但仍需检查链接与 staged diff。

提交前按矩阵逐项核对，不能只看“69 passed”之类历史数字。出现既有缺陷也要定位并记录归属，必要时修复后重验；不能以“不是本篇引入”放行缺失的累计验收。缺环境时保留待验证/未通过状态，并报告具体缺项。
